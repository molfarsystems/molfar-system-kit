## How long each source keeps data

GitHub Insights → Traffic shows views, unique visitors, full clones, and unique cloners for the past 14 days, in UTC. Referring sites and popular content are a rolling top list for those same 14 days, updated daily, with no per-day dates. Search engines and GitHub itself are excluded from referrers. [Viewing traffic to a repository](https://docs.github.com/repositories/viewing-activity-and-data-for-your-repository/viewing-traffic-to-a-repository), [Traffic API](https://docs.github.com/rest/metrics/traffic). [[1]](https://docs.github.com/enterprise-cloud@latest/repositories/viewing-activity-and-data-for-your-repository/viewing-traffic-to-a-repository) [[2]](https://docs.github.com/rest/metrics/traffic)

Write GitHub traffic down at least every 7 days, and on the day you return from a gap. A gap of 15 days or more with no snapshot deletes the early days. Stars, forks, Discussions, and issues stay on the repository page. I did not find a retention limit for those counts.

Play Console Statistics still holds user acquisitions, and store-listing acquisitions remain in Statistics and CSV exports. Since July 2026 the store-listing screens emphasize install clicks, not completed installs. [Understand and grow your app's user base](https://support.google.com/googleplay/android-developer/answer/9859173). [[3]](https://support.google.com/googleplay/android-developer/answer/9859173) I did not find an official deletion date for those Statistics totals. Write the weekly number anyway.

On the website, Google Analytics standard reports are not cut by the retention setting. Event-level explorations default to 2 months and can be set to 14 months on a free property. [Data retention](https://support.google.com/analytics/answer/7667196). [[4]](https://support.google.com/analytics/answer/7667196?hl=en&ref_topic=9303569) On day 1, in Admin, set Data retention to 14 months if the menu allows it.

Discord Server Insights, where it exists, goes back 120 days for an ordinary server, and some charts start only after 500 members. [Server Insights FAQ](https://support.discord.com/hc/en-us/articles/360032807371-Server-Insights-FAQ). [[5]](https://support.discord.com/hc/th/articles/360032807371-Server-Insights-FAQ) This server is small, so expect no Insights. The member count on screen has no history.

Telegram’s detailed channel statistics exist only for channels of a certain size. The exact limit is a server-side flag, not a number I can confirm. [Channel statistics](https://core.telegram.org/api/stats). [[6]](https://core.telegram.org/api/stats) The subscriber count under the channel title is a snapshot. Write it down.

## Six metrics

Check all six in the weekly pass. None of them is a statistical test. The counts will be too small for one.

1. **GitHub unique visitors, trailing 14 days.** Source: Insights → Traffic. Weekly, and on return. This is “people found the Kit.”
2. **GitHub unique cloners, same window.** Closest substitute for someone taking the files. A clone is not a pack install.
3. **Outside reactions.** New stars, plus Discussions, issues, issue comments, and submitted roles that are not you. Weekly, from the repository tabs. This is the brief’s “a few people outside the project.”
4. **Play user acquisitions, 28 days versus the prior 28 days.** Statistics. Weekly. This is “Molfar got new installs,” not “they installed a pack.”
5. **Website sessions with campaign `kit-launch`.** Traffic acquisition, dimension Session campaign, then Session source / medium. Weekly. This is which channel brought site visits. [URL builders](https://support.google.com/analytics/answer/10917952). [[9]](https://support.google.com/analytics/answer/10917952?hl=en)
6. **Play visits or acquisitions with a campaign UTM**, filter Ads and referrals, breakdown UTM source. Weekly after the first tagged link. Partial proof that a store visit came from a campaign link. [Play Console help](https://support.google.com/googleplay/android-developer/answer/9859173). [[3]](https://support.google.com/googleplay/android-developer/answer/9859173)

Discord and Telegram counts go in the sheet as context only. A change of one or two on a small channel is noise.

**Cannot measure.** The README tells people to use Download raw file on the zip in `roles/packs/`, not a release asset. GitHub does not count those raw-file downloads, nor the automatic source zip. Release assets do have a download count, but only if a file is uploaded as an asset. [About releases](https://docs.github.com/repositories/releasing-projects-on-github/about-releases). [[10]](https://help.github.com/articles/getting-the-download-count-for-your-releases/) The app has no analytics, so a pack install inside Molfar is invisible. Do not add a tracker to measure it. Substitutes are unique cloners, questions that show someone tried the install steps, and submitted roles.

## Week-4 thresholds

Compare with the day-1 sheet. If the day-1 14-day unique visitors are already above 30, drop the floor of 30 and keep the multiple.

**Worked** if at least 3 of these 4 are true:

- A saved 14-day unique-visitor total is at least 30, and at least 3 times the day-1 14-day unique visitors.
- Net new stars are at least 5.
- At least 3 outside replies: a Discussion, an issue, a comment, or a submitted role. Stars do not count in this row.
- Play user acquisitions for the campaign 28 days are at least 5 above the prior 28 days, or at least 3 acquisitions carry a campaign UTM.

**Did not work** only if all of these are true: no saved 14-day window is more than 10 unique visitors above day 1, net stars are under 2, outside replies are zero, and Play acquisitions are not above the prior 28 days.

**Unclear** is the rest, including a lost GitHub window. Do not score a missing snapshot as failure.

Reasoning: the October Show HN had no traction, the Kit is new, and the time budget is about 4 hours a week. Thirty visitors in 14 days is about two people a day. Five stars and three replies is “a few people,” which is the brief’s direction, not a growth target. Raise the floors if day 1 is already busier than this. These are judgment bands. A miss of one star is not a finding.
